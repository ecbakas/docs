# Native card scan in the refund confirm sheet — design

**Repo:** `super-app` · **Date:** 2026-09-24 · **Branch:** `feat/native-card-scan`
(cut from `fix/refund-and-tag-list-backlog` @ `231c1f6`)

## Goal

Test the platforms' own card scanners against the app's ML Kit OCR scan
("Scan card"). This phase adds **one more capture tile** to the refund confirm
sheet; "Tap card" and "Scan card" stay exactly as they are.

- **Android:** Google Pay's payment card recognition (`play-services-wallet`).
- **iOS:** VisionKit `DataScannerViewController` (iOS 16+) plus a native
  regex/Luhn parser.

**Where this is headed (not built now):** if native scanning works well, it
becomes the primary scan and "Scan card" becomes the fallback for devices that
cannot run it. This phase is designed to make that switch a JS-only change:
the availability check and the fallback-relevant error codes ship now, so the
later switch needs no native rebuild.

## REVISED 2026-09-24 — native-first "Scan card" is built on this branch

The user pulled the fallback phase in before device testing:

1. "Native scan" is renamed back to **"Scan card"**. There is one scan tile.
2. The picker checks, once on mount, whether native scanning is usable, with
   `CardScannerModule.isAvailableAsync()`. It is usable only when all of these
   hold:
   - the module is in the build;
   - it reads real cards: each native module now exposes an `environment`
     constant, and Google Pay **TEST counts as unavailable** because it
     returns a placeholder;
   - `isSupportedAsync()` passes.
3. Pressing "Scan card":
   - **Native usable:** it opens the native scanner. Any failure except a
     cancel is logged and falls back to the existing OCR scan, and the picker
     then stays on OCR.
   - **Not usable, or the check has not resolved yet:** it opens the OCR scan
     directly, as before.
   - A result marked `test` is discarded, and OCR opens instead.

Consequences:
- **Android always uses the OCR scan** until the wallet environment is switched
  to PRODUCTION, which needs Google Pay production access.
- **iOS 16+ devices with DataScanner support go native.**
- The separate tile, its error lines, the placeholder warning and the
  placeholder Confirm gate are all removed, along with their seven i18n keys.
  A TEST card can no longer reach the fields.

This supersedes the "every build", separate-tile, error-caption and
placeholder-warning parts of the UI section below.

## Decisions taken

| Question | Answer |
|---|---|
| Classic RN bridge (`.m`, `ActivityEventListener`, `WritableMap`) or Expo Modules API? | **Expo Modules API.** `android/` and `ios/` are gitignored and regenerated by prebuild, so native code must live in an autolinked module. Expo 54 autolinks `./modules` by default (`expo-modules-autolinking` `nativeModulesDir`). No `.m` file; `OnActivityResult` replaces `ActivityEventListener`; results reach JS as plain objects. |
| Which builds show the tile? | **Every build.** The user's call. The TEST-environment risk below is mitigated by a warning line instead of by hiding the tile. |
| Where is the work done? | New branch in the main `super-app` checkout, so the user's build picks it up directly. |
| PAN length | **13–19 digits**, matching `parse-card-ocr.ts`, not 13–16: 19-digit Visa/Maestro/UnionPay PANs exist. |

## Known risks and limits

1. **Google Pay TEST returns a placeholder card.** A third-party write-up says
   that under `ENVIRONMENT_TEST` the recognizer "always returns a stub result
   if it recognizes the card", and that real recognition needs Google Pay API
   **production access** (Google Pay & Wallet Console approval for
   `com.clomerce.unirefundsuperapp` and its signing key). Google's own page
   for the feature returned 404 during design, so this is **reported, not
   confirmed**. It is verified on-device in QA. If true, the Android tile in
   TEST proves the plumbing, not recognition quality, and **Android cannot
   become the primary scan until production access is granted.**
2. **The placeholder passes Luhn**, and the tile ships in every build, so a
   placeholder could be submitted as a real payout. Mitigation: the result
   carries `environment`, and a `"test"` result shows a persistent warning
   under the card fields (see UI).
3. **Android cannot report a camera refusal.** The recognizer runs inside Play
   Services and asks for the camera itself; a refusal there reaches us as a
   plain cancel. So `E_PERMISSION_DENIED` is iOS-only, and a future
   native-first flow cannot auto-fall back on a refusal on Android.
4. **iOS 15.x always gets `E_UNSUPPORTED`.** The app's deployment target is
   15.5 (`expo-build-properties`); DataScanner needs 16.0 and an A12 chip or
   later.
5. **Native code means a new dev client** on both platforms. Metro alone
   cannot deliver it, and an old dev client gets `E_MODULE_MISSING`.

Both workspace Android devices have Play Services (`com.google.android.gms`
26.32.34 on `LD38266200649` and `VA08263HJ1120`, checked 2026-09-24).

## Architecture

```
modules/card-scanner/                  native only, autolinked
  expo-module.config.json              android + apple, module name "CardScanner"
  android/build.gradle                 + com.google.android.gms:play-services-wallet
  android/src/main/java/expo/modules/cardscanner/CardScannerModule.kt
  ios/CardScanner.podspec              frameworks: VisionKit, AVFoundation
  ios/CardScannerModule.swift          availability, permission, presentation, promise
  ios/CardScanViewController.swift     DataScanner host + Cancel bar button
  ios/CardTextParser.swift             PAN (regex + Luhn) and expiry extraction
src/utils/card/native-card-scanner.ts  the TypeScript API (inside src/ for @/, jest, tsc)
```

The JS wrapper reaches the module with `requireOptionalNativeModule("CardScanner")`,
so a build without it degrades to a coded rejection instead of throwing at import.

### TypeScript API

```ts
export type NativeCardScanResult = {
  pan: string;
  expiryMonth?: number; // 1–12
  expiryYear?: number; // 4-digit
  environment: "test" | "production" | "device";
};

export type NativeCardScanErrorCode =
  | "E_CANCELLED"
  | "E_PERMISSION_DENIED"
  | "E_UNSUPPORTED"
  | "E_UNAVAILABLE"
  | "E_BUSY"
  | "E_SCAN_FAILED"
  | "E_MODULE_MISSING";

export const CardScannerModule: {
  startScan(): Promise<NativeCardScanResult>;
  isSupportedAsync(): Promise<boolean>;
};

export function nativeScanErrorCode(err: unknown): NativeCardScanErrorCode;
```

`environment` is `"test"` or `"production"` on Android (the Wallet environment
used) and `"device"` on iOS (on-device recognition, no environment).

| Code | Meaning | Future native-first flow |
|---|---|---|
| `E_CANCELLED` | user backed out (Android: also a camera refusal) | never fall back |
| `E_BUSY` | a scan is already running | never fall back |
| `E_PERMISSION_DENIED` | iOS camera access denied or restricted | point to Settings |
| `E_UNSUPPORTED` | OS too old, hardware unsupported, Play Services / API unavailable | fall back to Scan card |
| `E_UNAVAILABLE` | iOS: supported but `isAvailable` false after permission; Android: no current activity to launch from | fall back to Scan card |
| `E_MODULE_MISSING` | native module absent (stale dev client, Expo Go) | fall back to Scan card |
| `E_SCAN_FAILED` | anything else, incl. OK with no parseable result | offer Scan card |

### Android — `CardScannerModule.kt`

- `Wallet.getPaymentsClient(activity, WalletOptions.Builder().setEnvironment(WalletConstants.ENVIRONMENT_TEST).build())`,
  with a comment on switching to `ENVIRONMENT_PRODUCTION` (needs production
  access for the package and signing key). The environment is one constant, and
  `environment` in the result is derived from it.
- `startScan`: `getPaymentCardRecognitionIntent(PaymentCardRecognitionIntentRequest.getDefaultInstance())`.
  On success, launch the response's pending intent's `intentSender` with
  `startIntentSenderForResult` under a private request code. On task failure,
  reject `E_UNSUPPORTED`.
- `OnActivityResult`: match the request code. `RESULT_OK` goes to
  `PaymentCardRecognitionResult.getFromIntent(data)`, which gives the PAN and
  `creditCardExpirationDate?.month/.year`. A missing or empty result rejects
  `E_SCAN_FAILED`; `RESULT_CANCELED` rejects `E_CANCELLED`.
- `isSupportedAsync`: the same intent request, resolved `true` on success and
  `false` on failure, **without launching**.
- One pending promise at a time; a second `startScan` rejects `E_BUSY`. No
  current activity rejects `E_UNAVAILABLE`.
- Class and method names are checked against the published AAR with `javap`
  before writing, because Google's reference pages do not render for fetch
  tools.

### iOS — `CardScannerModule.swift` and friends

- `AsyncFunction("startScan")` runs on the main queue.
  1. `if #available(iOS 16.0, *)` fails, or `!DataScannerViewController.isSupported`: reject `E_UNSUPPORTED`.
  2. Camera authorization: `.notDetermined` asks via `AVCaptureDevice.requestAccess(for: .video)`; `.denied`/`.restricted` rejects `E_PERMISSION_DENIED`.
  3. `!DataScannerViewController.isAvailable` rejects `E_UNAVAILABLE`.
  4. Present `CardScanViewController` full screen from the **top-most presented
     view controller**. The confirm sheet is itself an RN `Modal`, so the root
     view controller is the wrong presenter.
- `CardScanViewController` embeds `DataScannerViewController(recognizedDataTypes: [.text()], qualityLevel: .accurate, recognizesMultipleItems: true, isHighlightingEnabled: true)`
  in a `UINavigationController` with a **Cancel** bar button. DataScanner draws
  no close control of its own, and a scanner with no way out is the Didit 3.2.0
  bug this app already shipped once. Full-screen presentation means no
  swipe-to-dismiss path to miss.
- Completion:
  - **Live**: on `didAdd` / `didUpdate`, run `CardTextParser` over all current
    text items. On the first Luhn-valid PAN: finish now if an expiry is present,
    otherwise keep scanning up to ~1.5 s for one, then finish with the PAN alone.
  - **Tap**: `didTapOn` re-runs the parser immediately; a PAN finishes at once.
- `CardTextParser`: PAN `(?:\d[ -]?){13,19}` with separators stripped, Luhn
  required, per line first and joined lines only as a fallback. Expiry
  `(0[1-9]|1[0-2])\s*/\s*(\d{2}|\d{4})`, preferring one near
  `GOOD THRU|VALID|EXPIRES`. This mirrors `parse-card-ocr.ts`.
- `isSupportedAsync`: iOS 16+ and `isSupported`. It does not prompt for the
  camera.
- Scanned text and PANs are never logged (the rule `scan-failure.ts` states).

## UI — `RefundPayoutStep.tsx`

- The card capture block (the tiles, both inputs and the hint) is drawn twice
  today (sole-option branch and the "different card" row) with identical JSX.
  It is written once as a JSX value and placed in both; only one renders at a
  time. Tap and Scan are unchanged; **"Native scan"** (`scan-outline`) is
  appended. *(Revised while planning: originally a `CardCaptureTiles`
  component for the tile row only.)*
- Pressing it sets `entry` to `"native"` and calls `startScan()`. The tile is
  disabled while a scan is in flight.
- Success goes through the existing `applyScan`: the number via
  `formatCardNumber`, and the expiry via `formatExpiryFromParts(month, year)`
  only when both parts are present. Confirm's Luhn and expiry gate is unchanged.
- Errors show as one `tone="error"` caption under the tiles. Toasts render
  behind this Modal, so they are not an option. The caption clears on the next
  tile press or on success. `E_CANCELLED` shows nothing, and neither does
  `E_BUSY`: it only means the first scan is still open.
- A `"test"` result shows a `tone="warning"` caption under the card fields
  until the number is edited or another capture replaces it.

## Testing

**Automated (runs here):**
- `src/utils/card/__tests__/native-card-scanner.test.ts` (node project):
  - error normalisation from Expo `CodedError.code`
  - `E_MODULE_MISSING` when the native module is null
  - result passthrough
  - `isSupportedAsync` is false when the module is missing
- `RefundPayoutStep.router.test.tsx`, in the existing mock style:
  - the tile shows in both branches
  - success fills the number and expiry
  - PAN-only leaves the expiry alone
  - cancel is silent
  - each error code shows its message
  - the TEST warning shows, and clears on edit
  - the tile is disabled mid-scan
- Gates: `npm run typecheck`, `npm test`, `npm run lint`, against baselines
  **re-measured before the first change** (the AGENTS.md figures are from
  2026-09-10).

**Unverified until the user builds:**
- Kotlin compiles only in the user's build. The agent does not run
  gradle/expo builds; the handover is `npm run android:dc` (a new module needs
  a clean prebuild).
- Swift, including `CardTextParser`, needs a Mac: `npm run ios:pc` or a
  TestFlight `dry_run`. The repo has no Swift test harness.

**Device QA (Android, after the user's build):** CPadNFC `LD38266200649`, only
after checking no other session owns it (`adb reverse --list`, host listening
ports, foreground activity):
- a real card, which settles risk 1
- cancel
- a camera refusal inside Google's screen, which settles risk 3
- a double tap
- the TEST warning
- Tap and Scan still unchanged

## Out of scope

- Making native the primary scan with OCR fallback (the next phase, gated on
  this test and, for Android, on production access).
- Google Pay production access.
- Wiring the tile into My Cards or any other capture surface.
