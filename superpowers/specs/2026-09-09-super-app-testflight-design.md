# super-app: TestFlight delivery from a self-hosted macOS runner

**Date:** 2026-09-09
**Scope:** `super-app` (`unirefund-mobile`) — a new `.github/workflows/testflight.yml`,
two edits to existing app config (`app.config.js`, `withSigningTeam.js`), and a
provisioning runbook at `docs/testflight.md`. Android is out of scope.

## Problem

`super-app` has no CI at all. There is no `.github` directory, no `eas.json`, no
`eas-cli` dependency, no `extra.eas.projectId` and no `owner` — EAS was never set
up — and no fastlane. Every iOS build to date has been produced by hand on a
developer's mac, which means TestFlight delivery is undocumented, unrepeatable,
and gated on one person's machine state.

The repo is nonetheless close to ready. HEAD (`c4bac9d feat:ios build`,
2026-09-09) added [`withSigningTeam.js`](../../../super-app/withSigningTeam.js),
which pins `DEVELOPMENT_TEAM` so a prebuilt `ios/` project can sign at all, and
`withDiditBitcodeStrip.js` already solves an App Store rejection someone hit for
real — its header quotes the verbatim error:

```
ContentDelivery Code=90482 — Invalid Executable. The executable
'UnirefundSuperapp.app/Frameworks/OpenSSL.framework/OpenSSL' contains bitcode.
```

So the work is a pipeline, not a port.

## Constraints discovered in the repo

| Fact | Consequence for the pipeline |
| --- | --- |
| `/ios` **and** `/android` are both in `.gitignore` | This is a prebuild workflow. CI must run `expo prebuild`; there is no committed Xcode project to archive. |
| `withDiditBitcodeStrip.js` hooks the Podfile's `post_install` | `pod install` **must** run in CI. A cached or committed `ios/` would skip the strip and reproduce the 90482 rejection. `prebuild` runs `pod install` on macOS. |
| `withSigningTeam.js` filters build configurations by `PRODUCT_BUNDLE_IDENTIFIER` | The app target can be configured in isolation from the Pods targets. This is load-bearing — see "Manual signing" below. |
| `app.config.js` has `version: "1.0.0"` and **no** `ios.buildNumber` | Every archive would be `CFBundleVersion` `1`. TestFlight rejects a duplicate build number for a given version, so the second upload fails. |
| `package-lock.json:5901` resolves `@unirefund/qr` as `git+ssh://git@github.com/…` | `npm ci` attempts SSH and fails without a deploy key on the runner. |
| `ayasofyazilim-clomerce/unirefund-qr` returns HTTP 200 unauthenticated | It is public, so the SSH pin can be rewritten to HTTPS instead of managing a key. |
| `ayasofyazilim-clomerce/unirefund-mobile` is **private** | Precondition for a self-hosted runner is met. |
| The repo has 0 registered runners, 0 secrets, 0 environments | Everything below is new; nothing to migrate. |
| `init.ts` reads `.env` via dotenv and always fetches from `dev-api.<domain>` | Step order is fixed: write `.env`, `npm ci`, `npm run init`. The runner needs egress to `dev-api.unirefund.com`. |
| `src/utils/environment.ts` switches gateway at **runtime** (staff login + debug menu), defaulting to `dev`; only the apex domain is baked in | **No per-environment build matrix.** One IPA serves dev/uat/live. This is the significant divergence from `web-app`'s `deploy.yml`, which needs one image per environment because `init.ts` bakes gateway data into the artifact there. |
| `AGENTS.md` records `npm test` as **1 suite failing deterministically** (`tokens.test.ts`, 3 of 4 assertions) plus a load-dependent flake (`CardScannerModal.router.test.tsx`) | `npm test` cannot exit 0 and therefore cannot be a gate. `npm run typecheck` (clean) and `npm run lint` (0 errors / 89 warnings) can. |
| `expo.name` is `"Unirefund"`, but `withDiditBitcodeStrip.js` quotes a product name of `UnirefundSuperapp` | The Xcode scheme name is generated by `prebuild` and the two sources disagree. Do not hardcode it; read it back. |

## Decisions

Each was chosen against alternatives; the rejected options are recorded so a
future reader does not re-litigate them.

**Toolchain: raw `xcodebuild` + `xcrun altool`.** Rejected `eas build --local`
(requires creating an Expo account, org and project id, and EAS-managed
credentials would move signing material to a third party) and fastlane (adds a
Ruby toolchain and a second config language for a single lane). The chosen path
adds no account, no runtime and no service; every secret stays in GitHub.

**Signing: distribution cert + profile in GitHub secrets, imported into a
throwaway keychain per run.** Rejected installing the identity by hand on the
runner once — zero secrets in GitHub, but the identity becomes invisible
machine state that expires in a year with no record of how it arrived, and does
not survive replacing the mac. Rejected automatic signing via
`-allowProvisioningUpdates` — it mutates the Apple Developer account from a
build script and can consume distribution-certificate slots (limit 3).

**Trigger: `workflow_dispatch` only. Build number: `github.run_number`.**
Rejected push-to-`main` — an iOS archive is 20–40 min on one serialised runner
and every TestFlight upload notifies testers, so per-merge delivery is both slow
and noisy. Rejected querying App Store Connect for latest-build-number+1, which
is more correct but needs JWT signing in the workflow; `run_number` is monotonic
and needs no network. A `build_number` dispatch input covers the rare override.

**Gates: `typecheck` + `lint` only.** Rejected running `npm test` with the
failure tolerated — a gate allowed to fail is not a gate, and a red X on every
release trains the team to ignore it. Rejected excluding `tokens.test.ts` via a
jest ignore pattern: it would gate honestly on the other 191 suites, but the
exclusion needs maintaining and the `CardScannerModal` flake can still fail a
release at random. The workflow will carry a comment naming `tokens.test.ts` as
the reason and the condition for re-adding the step.

## Source changes

### 1. `app.config.js` — a build number that exists

Inside `ios`:

```js
// TestFlight rejects a duplicate CFBundleVersion for a given `version`, so CI
// feeds github.run_number in (see .github/workflows/testflight.yml). Local
// builds never upload and do not care, so they get "1".
buildNumber: process.env.IOS_BUILD_NUMBER?.trim() || "1",
```

`version` stays `"1.0.0"` and remains the hand-edited marketing version.

### 2. `withSigningTeam.js` — manual signing, app target only

The obvious approach — passing `CODE_SIGN_STYLE=Manual
PROVISIONING_PROFILE_SPECIFIER=…` on the `xcodebuild` command line — **breaks
this project**. Command-line build settings apply to every target in the
workspace, so each CocoaPods target inherits a profile whose bundle identifier
is `com.clomerce.unirefundsuperapp` and the archive fails with *"Provisioning
profile doesn't include the bundle identifier org.cocoapods.…"*.

`withSigningTeam.js` already filters configurations by
`PRODUCT_BUNDLE_IDENTIFIER` precisely to avoid touching the Pods targets, so the
signing switch belongs there, gated on an environment variable set only by CI:

```js
const TEAM_ID = process.env.EXPO_APPLE_TEAM_ID?.trim() || "SMN73535BW";
// Set only by CI. Local device builds keep Automatic signing, which resolves
// through an Xcode-authenticated Apple ID; CI has no such session and instead
// imports a distribution certificate and a *named* profile into a throwaway
// keychain, which only manual signing will select.
const PROFILE = process.env.EXPO_IOS_PROVISIONING_PROFILE?.trim();
```

and, replacing the two unconditional assignments inside the existing
per-configuration loop:

```js
if (PROFILE) {
  buildSettings.CODE_SIGN_STYLE = "Manual";
  buildSettings.PROVISIONING_PROFILE_SPECIFIER = `"${PROFILE}"`;
  buildSettings.CODE_SIGN_IDENTITY = '"Apple Distribution"';
} else {
  buildSettings.CODE_SIGN_STYLE = "Automatic";
}
buildSettings.DEVELOPMENT_TEAM = TEAM_ID;
```

The `project.addTargetAttribute("DevelopmentTeam", TEAM_ID)` call is unchanged.
With `EXPO_IOS_PROVISIONING_PROFILE` unset the emitted project is byte-identical
to today's, so `npm run ios` and `npm run android` are unaffected: the CI path is
purely additive.

Note the quoting. `xcode`'s pbxproj writer does not add quotes around values, and
a profile name contains spaces, so the value must arrive pre-quoted — matching how
`CODE_SIGN_IDENTITY` is written.

## The workflow

`.github/workflows/testflight.yml`, commented to the density of
`web-app/.github/workflows/deploy.yml`.

```yaml
on:
  workflow_dispatch:
    inputs:
      dry_run:       # archive, export and --validate-app, then stop
      build_number:  # optional override of github.run_number

concurrency: { group: testflight, cancel-in-progress: false }
permissions: { contents: read }

jobs:
  testflight:
    runs-on: [self-hosted, macOS, macos-testflight]
    environment: testflight
    timeout-minutes: 90
```

`cancel-in-progress: false`: cancelling mid-archive would leave a keychain and a
provisioning profile behind on a persistent machine, since the cleanup step
would never run.

| # | Step | Rationale |
| --- | --- | --- |
| 1 | `actions/checkout` (SHA-pinned, default `clean: true`) | `clean` runs `git clean -ffdx`, and `-x` removes ignored files — so a stale `ios/` or `node_modules` from the previous run cannot poison this one. A self-hosted workspace is reused; a hosted one is not. |
| 2 | `actions/setup-node` (SHA-pinned) with `node-version: 20` | matches `.nvmrc` and `engines.node` |
| 3 | `git config --global url."https://github.com/".insteadOf ssh://git@github.com/` | rewrites the `@unirefund/qr` SSH pin; the repo is public so no key is needed |
| 4 | Write `.env` from secrets | `init.ts` reads `.env` via dotenv; `EXPO_PUBLIC_*` are inlined at bundle time |
| 5 | `npm ci` | lockfile-exact install |
| 6 | `npm run init` | writes the gitignored `src/data/**/*.gen.json` that `TranslationKey` derives from. Without it `tsc` fails on the import (TS2307) rather than naming the missing codegen |
| 7 | `npm run typecheck`, then `npm run lint` | the agreed gates; ~2 min spent before a 30 min archive |
| 8 | `npx expo prebuild --platform ios --clean` | generates `ios/` and runs `pod install`, which is what fires the Didit bitcode strip. `EXPO_IOS_PROVISIONING_PROFILE` is exported here — this is where the plugin flips to Manual |
| 9 | Keychain setup | run-unique keychain name; password from `openssl rand`; import the `.p12`; `security set-key-partition-list`; `security set-keychain-settings -lut 21600`; add to the search list; copy the profile into `~/Library/MobileDevice/Provisioning Profiles/` |
| 10 | Resolve workspace and scheme from `xcodebuild -list -json` | the scheme is generated by `prebuild`, and `app.config.js` (`Unirefund`) disagrees with the product name in `withDiditBitcodeStrip.js` (`UnirefundSuperapp`). Reading it back removes the guess |
| 11 | `xcodebuild archive -destination 'generic/platform=iOS' -configuration Release` | **no signing settings on the command line** — step 2 of the source changes put them on the app target only |
| 12 | `xcodebuild -exportArchive -exportOptionsPlist` | `method: app-store-connect`, `signingStyle: manual`, `provisioningProfiles: { com.clomerce.unirefundsuperapp: <name> }`, `teamID`, `uploadSymbols: true`. `app-store-connect` is the post-Xcode-15.3 spelling of what used to be `app-store`; the Xcode 16.1 floor above means the new name is safe, and the old one only warns |
| 13 | `xcrun altool --validate-app` | catches 90482-class rejections before a build number is consumed |
| 14 | `xcrun altool --upload-app` — skipped when `dry_run` | the only irreversible step in the job |
| 15 | `if: always()` teardown | `security delete-keychain`; restore the previous keychain search list; remove the installed profile by UUID; delete the `.p8`, `.p12` and `.env` |
| 16 | Upload `.ipa` + dSYMs as a run artifact; write `$GITHUB_STEP_SUMMARY` | mirrors the summarise step in `web-app`'s `deploy.yml` |

`dry_run` carries more weight than it appears to: it exercises the entire
signing chain and produces a validated IPA **without** consuming a build number
or notifying testers. It is how runs 1–4 get debugged quietly.

### Keychain details that decide whether this works

- **`security set-key-partition-list -S apple-tool:,apple: -s -k <pw> <keychain>`
  is mandatory.** Without it `codesign` raises a GUI keychain-access prompt on a
  headless mac, and the job hangs until the 90-minute timeout instead of failing.
  This is the single most common cause of a first-attempt iOS CI job that never
  returns.
- **`-lut 21600`** (and `security unlock-keychain`) stops the keychain
  auto-locking part-way through a long archive.
- **The keychain must be added to the search list** (`security list-keychains -s`)
  or `codesign` will not look in it. The teardown must restore the previous list.

### `altool` key placement

`altool` locates its App Store Connect key by *filename*, searching
`./private_keys`, `~/private_keys`, `~/.private_keys` and
`~/.appstoreconnect/private_keys` for `AuthKey_<KEY_ID>.p8`. The workflow writes
it to `~/.appstoreconnect/private_keys/` — which is **outside** the workspace and
therefore outside the reach of the next run's `git clean`. Deleting it in the
`always()` teardown is not optional.

## Security posture

1. **`environment: testflight` with required reviewers.** Secrets decrypt only
   for jobs targeting that environment, and a dispatch waits for approval.
   Without it, write access to the repo is sufficient to ship to testers' devices.
   It is also the audit trail of who released what. Configuring the reviewer list
   is GitHub UI work, deliberately not expressible in YAML — the same caveat
   `web-app`'s `deploy.yml` records for its prod environment.
2. **A dedicated `macos-testflight` runner label, not bare `self-hosted`.** The
   risk from a registered runner is not this workflow but the next one someone
   adds with `runs-on: self-hosted` and a `pull_request` trigger. A specific
   label makes borrowing the machine deliberate.
3. **Least-privilege App Store Connect key: `Developer` role**, which suffices to
   upload a build. An `Admin` or `Account Holder` key reachable from a build
   script could also change team membership and pricing. Documented fallback: if
   Apple returns 403 on upload, `App Manager` is the next step up — do not jump
   to `Admin`.
4. **Secret material lands in `$RUNNER_TEMP`, never the workspace**, created with
   `install -m 600 /dev/null <path>` before anything is written into it, and
   deleted in `always()`. Two paths escape the workspace and need explicit
   removal: the `altool` key in `~/.appstoreconnect/private_keys/`, and the
   provisioning profile in `~/Library/MobileDevice/Provisioning Profiles/`.
   To be precise about what this buys: the controls are the `0600` mode, the
   non-admin runner user, FileVault, and the short lifetime — *not* secure
   erasure. `rm -P` overwrites nothing reliably on APFS, so the spec does not
   claim it; a compromised runner host is assumed to be a full compromise of
   whatever it built with.
5. **The synthesised `.env` is gitignored, which means it survives between runs**
   on a persistent machine — `git clean -ffdx` at the *start* of the next run is
   too late to be the only defence. Removed in teardown.
6. **First-party actions pinned to commit SHAs.** `actions/checkout` and
   `actions/setup-node` are the only two actions used; a tag is mutable, a SHA is
   not.
7. **No secret is ever echoed to a step's log.** GitHub masks registered secret
   values, but base64 material is chunked and reflowed by shell tooling in ways
   that defeat masking, so the workflow never prints one, not even truncated.

Accepted, not fixed: `EXPO_PUBLIC_EXTRACTION_API_KEY` is inlined into the JS
bundle and readable out of the shipped IPA. That is a settled product decision
(server-side proxying was considered and rejected) and is already documented in
`.env.example`. The pipeline does not worsen it; it must not be cited as a
pipeline defect.

## Secrets

Signing and upload — 7:

| Secret | Origin |
| --- | --- |
| `IOS_DIST_CERT_P12_BASE64` | Xcode → Settings → Accounts → Manage Certificates → export Apple Distribution, then `base64 -i cert.p12` |
| `IOS_DIST_CERT_PASSWORD` | the password set on that export |
| `IOS_PROVISIONING_PROFILE_BASE64` | App Store profile for `com.clomerce.unirefundsuperapp` |
| `IOS_PROVISIONING_PROFILE_NAME` | the profile's exact name — what `PROVISIONING_PROFILE_SPECIFIER` matches |
| `ASC_API_KEY_P8_BASE64` | ASC → Users and Access → Integrations → Keys, **Developer** role. Downloadable once |
| `ASC_API_KEY_ID` | shown beside the key |
| `ASC_ISSUER_ID` | shown above the key list |

Build configuration — 8: `GATEWAY_URL`, `SUPPORTED_LOCALES`,
`EXPO_PUBLIC_GATEWAY_URL`, `EXPO_PUBLIC_OAUTH_CLIENT_ID`,
`EXPO_PUBLIC_DEEP_LINK_HOST`, `EXPO_PUBLIC_EXTRACTION_URL`,
`EXPO_PUBLIC_EXTRACTION_API_KEY`, `EXPO_PUBLIC_EXTRACTION_PROJECT_ID`.

Optional: `EXPO_APPLE_TEAM_ID`, which overrides the `SMN73535BW` default in
`withSigningTeam.js`.

`SUPPORTED_LOCALES` must stay a superset of every runtime value, because it
decides which i18n bundles `init.ts` generates — the same constraint `web-app`
documents for its own deploy.

## Runner provisioning (`docs/testflight.md`)

Hardware and tooling: Apple silicon mac; **Xcode 16.1 or newer** (required by
Expo 54 / RN 0.81 with `deploymentTarget: "15.5"`); CocoaPods; Node 20; roughly
60 GB free for Xcode, the iOS SDK, DerivedData and the Pods cache.

Host setup: a dedicated **non-admin** macOS user account for the runner;
FileVault enabled; automatic login disabled. Install the GitHub Actions runner as
a launchd service under that user with the label `macos-testflight`. Accept the
Xcode licence (`sudo xcodebuild -license accept`) and download the iOS platform
SDK once interactively — the first `xcodebuild` invocation on a fresh Xcode
prompts, and a prompt on a headless machine is an eventual timeout.

Network: outbound reachability to `dev-api.unirefund.com` (for `npm run init`),
`github.com`, `registry.npmjs.org`, `cdn.cocoapods.org` and Apple's upload
endpoints.

The runbook also records: how to produce each of the 15 secrets, the annual
certificate and profile rotation (both expire; the failure mode is a signing
error, not a warning), and the `dry_run` procedure for validating a change to the
pipeline without shipping.

## Verification

The pipeline cannot be executed from the development environment this was written
in (Windows). What is verifiable, and where:

**Locally, before handoff:**

1. `actionlint` over `testflight.yml` — catches expression, context and schema
   errors, including the `secrets`-in-`if` class of mistake.
2. A Node assertion that `app.config.js` yields `buildNumber` `"1"` with
   `IOS_BUILD_NUMBER` unset and the injected value when set.
3. A Node assertion that `withSigningTeam.js` emits `CODE_SIGN_STYLE: "Manual"`
   plus a quoted `PROVISIONING_PROFILE_SPECIFIER` when
   `EXPO_IOS_PROVISIONING_PROFILE` is set, and `"Automatic"` with no specifier
   when it is not — driven against a stub pbxproj rather than a real prebuild.
4. `npm run typecheck` and `npm run lint` in `super-app`, to confirm the two
   source edits hold the `AGENTS.md` baselines (typecheck clean; lint 0 errors).

**Only on the runner, via `dry_run: true`:** everything from step 8 onward —
prebuild, `pod install` and the bitcode strip, keychain import, scheme
resolution, archive, export, and `altool --validate-app`.

**Only by a real dispatch:** the upload itself, App Store Connect processing, and
the export-compliance answer that `usesNonExemptEncryption: false` is supposed to
pre-fill.

This distinction is stated plainly here so the pipeline is not described as
proven when it has only been linted. The first genuine green `dry_run` on the mac
is the point at which the design is validated; until then it is a design.

## Out of scope

- Android / Play Store delivery. The same job shape would work, but it needs its
  own keystore-secret decisions and no one has asked for it.
- Making `npm test` a gate. That is blocked on `tokens.test.ts`, whose pre-existing
  colour-token violations `AGENTS.md` already flags as welcome to fix in a
  dedicated PR.
- Automatic marketing-version bumps. `version` in `app.config.js` stays
  hand-edited; only `buildNumber` is derived.
