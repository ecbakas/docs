# Remove the deprecated providers — web-app (Plan 5)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Delete `useTenant`, `useGrantedPolicies`, `TenantProvider`, `GrantedPoliciesProvider`, the two `@deprecated` props, the dead `ConfigProvider` stubs, and the `MasterDataGridResourcesProvider` mount — leaving `ApplicationConfigurationProvider` as the single provider and `useApplicationConfiguration()` / `useLocalization()` as the only hooks.

**Architecture:** Plan 1 left the old hooks in place as adapters over the new provider. This removes them. 254 of the 267 consumers migrate as a one-line rename-on-destructure, so no usage code changes; only 13 need real edits. `tsc` across both apps plus a production build are the entire safety net.

**Tech Stack:** Next.js 16 App Router, React 19, TypeScript, pnpm workspaces.

**Spec:** `docs/superpowers/specs/2026-09-04-application-configuration-provider-design.md`

**Depends on:** plan 1 (`feat/app-config-provider`). This branch stacks on it, and its `web-utils` submodule PR (#48) must merge first.

## Global Constraints

- **No test in this repo can reach any file this plan touches.** The only unit gate is `apps/web`'s `node --import tsx --test "src/**/*.test.ts"` — `.ts` only, cannot execute JSX. So `tsc` on **both** apps and `pnpm run build` on **both** apps are the whole safety net. Treat them as the gate, deliberately, not incidentally.
- Baselines measured 2026-09-07 on `feat/app-config-provider`: `apps/web` type-check **0 errors**, `apps/ssr` type-check **0 errors**, `apps/web` `test:unit` **136 tests / 135 pass / 1 pre-existing skip**, root lint **exit 0, 0 errors, 948 warnings** (web 465, ssr 459, ayasofyazilim-ui 14, ui 10), root build **2 successful, 2 total**.

A worktree that has never been built reports phantom `TS2307`s on image imports. This worktree HAS been built, so the baseline is genuinely 0 — do not accept a non-zero count as "pre-existing".
- Never run `next build` while a `next dev` server is running on the same app: both use `apps/*/.next`, and the build replaces the dev chunks, sending the browser into a `ChunkLoadError` reload loop.
- `prettier --check` is not a gate: CRLF makes it fail repo-wide. Format only touched files, and never `--write` the repo.

- [ ] **Step 3: Create `localization.ts` in the submodule**

Move the map and function out of `tenant.tsx` **unchanged** — same five entries, same `"en-UK"` fallback:

```ts
export interface Localization {
  locale: string;
  timeZone: string;
  lang: string;
}

const countryToLocale = {
  GB: "en-GB",
  US: "en-US",
  IE: "en-IE",
  TR: "tr-TR",
  DE: "de-DE",
};

/**
 * Preserved verbatim from the former `TenantProvider`, `"en-UK"` fallback
 * included. That is not a valid BCP 47 tag, but it is what shipped and every
 * consumer has been reading it — changing it is a separate decision.
 */
export function getLocaleFromCountryCode(code2: string) {
  const upperCode = code2.toUpperCase();
  return upperCode in countryToLocale
    ? countryToLocale[upperCode as keyof typeof countryToLocale]
    : "en-UK";
}
```

- [ ] **Step 4: Re-export it from `logic.ts`**

Add `export * from "./localization";` alongside the existing re-exports. `logic.ts` must stay pure — no React.

- [ ] **Step 5: Give the provider `lang` and `useLocalization`**

In `provider.tsx`, add a second context for `lang`, take it as a required prop, and derive localization from the configuration:

```tsx
const LangContext = createContext<string>("en");

export function ApplicationConfigurationProvider({
  configuration,
  lang,
  children,
}: {
  configuration: ApplicationConfiguration;
  lang: string;
  children: ReactNode;
}) {
  useEffect(() => {
    localStorage.setItem(
      "countryCode2",
      configuration.country.countryCode2?.toLocaleLowerCase() || "us",
    );
    localStorage.setItem("tenantTimeZone", configuration.timeZone);
  }, [configuration.country.countryCode2, configuration.timeZone]);

  return (
    <ApplicationConfigurationContext.Provider value={configuration}>
      <LangContext.Provider value={lang}>{children}</LangContext.Provider>
    </ApplicationConfigurationContext.Provider>
  );
}

/**
 * What 109 of the 122 former `useTenant` consumers actually wanted.
 * `lang` is a route segment, not configuration, which is why it rides a
 * separate context rather than being folded into the contract.
 */
export function useLocalization(): Localization {
  const config = useContext(ApplicationConfigurationContext);
  const lang = useContext(LangContext);
  return useMemo(
    () => ({
      locale: getLocaleFromCountryCode(config.country.countryCode2 || "UK"),
      timeZone: config.timeZone,
      lang,
    }),
    [config.country.countryCode2, config.timeZone, lang],
  );
}
```

Note `|| "UK"` is carried over verbatim from `TenantProvider` — `"UK"` is not in the map, so it deliberately resolves to the `"en-UK"` fallback. Keep it.

The two `localStorage` writes move here from `TenantProvider`. Their readers are `packages/ui`'s address combobox (`countryCode2`) and `packages/ayasofyazilim-ui`'s date picker (`tenantTimeZone`) — both must keep working.

```tsx
export function useTenantDateFormatters() {
  const localization = useLocalization();
  return useMemo(
    () => ({
      formatToTenantDate: (
        date: string | Date,
        dateOptions?: Intl.DateTimeFormatOptions,
      ) =>
        formatToLocalizedDate({
          date,
          dateOptions,
          localization,
          timeZone: localization.timeZone,
        }),
      formatToTimezoneDate: (
        date: string | Date,
        timeZone?: string,
        dateOptions?: Intl.DateTimeFormatOptions,
      ) => formatToLocalizedDate({ date, dateOptions, localization, timeZone }),
    }),
    [localization],
  );
}
```

`formatToTenantDate` pins `timeZone: localization.timeZone`; `formatToTimezoneDate` passes the caller's value through so `undefined` still means the system zone. Both semantics are load-bearing — preserve them exactly.

`@repo/utils` already depends on `@repo/ayasofyazilim-ui`, so the import is fine.
